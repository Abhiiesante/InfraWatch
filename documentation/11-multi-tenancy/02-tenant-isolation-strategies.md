## Database Isolation

As detailed in [Prisma RLS Extensions](./01-prisma-rls-extensions.md), database isolation is enforced exclusively at the application layer via our custom Prisma extensions. 

To prevent ID Guessing attacks (Insecure Direct Object Reference - IDOR):
1. **Never Trust User Input for Tenant IDs:** The `tenantId` must ALWAYS be extracted from the cryptographically signed JWT token, never from the request body or URL path.
2. **Compound Keys:** If an ID is passed in the URL (e.g., `/api/v1/assets/100`), the query must be `WHERE id = 100 AND tenantId = req.tenantId`. If asset 100 belongs to another tenant, the query simply returns `Not Found`.

## S3 Bucket Isolation

We use a single shared S3 bucket for all tenants (`infrawatch-assets-production`).

Isolation is enforced using strict S3 Key (folder path) namespacing:
`s3://infrawatch-assets-production/tenant_{tenantId}/assets/{assetId}/image.jpg`

When the API generates a pre-signed URL for an upload or download, it forces the object key to include the `req.tenantId`. This makes it mathematically impossible for a user in Tenant A to overwrite or download an image belonging to Tenant B, because the API will simply not generate a pre-signed URL for that path.

## Cache Isolation

Redis is fundamentally a key-value store with no concept of RLS. 

To prevent cache poisoning, every Redis key generated by the application MUST be prefixed with the `tenantId`.

```typescript
// src/services/cache.service.ts
export function getCacheKey(tenantId: number, entity: string, id: string | number) {
  return `tenant:${tenantId}:${entity}:${id}`;
}

// Usage
const cacheKey = getCacheKey(req.tenantId, 'dashboard_metrics', 'weekly');
```
